## Description

Replace the current Purple/Pink `LightColorScheme` / `DarkColorScheme` in `ui/theme/Theme.kt` with a blue
scheme built from `Color.kt` (it already defines `ColorBlue = 0xFF2F70BC` and `ColorBlue2 = 0xFF35A0F5` —
reuse or extend these rather than inventing an unrelated palette). Force `dynamicColor = false` in
`MyApplicationTheme` — today it defaults to `true`, which makes `dynamicLightColorScheme` /
`dynamicDarkColorScheme` silently override any custom scheme on API 31+, so the PRD's "blue colour scheme"
requirement would otherwise have no visible effect on most devices. Confirm (do not rewire) that dark mode
already works: `MyApplicationTheme` is called with `darkTheme = isSystemInDarkTheme()` and every screen
renders through `CoreFragment`, so no new dark-mode plumbing is needed — just make sure the new blue
`DarkColorScheme` has adequate contrast.

This is the one task in the run that touches Home/Setting's visual appearance. It does not touch their
behavior, navigation, or reachability.

## Acceptance

- `ui/theme/Theme.kt`'s `MyApplicationTheme` no longer takes the dynamic-color branch (verify by reading
  the function body — `dynamicColor` parameter default is `false`, or the dynamic branch is removed
  entirely).
- `LightColorScheme` and `DarkColorScheme` both use blue primary/secondary values sourced from `Color.kt`.
- No behavioral change to `HomeFragment` or `SettingFragment` — they still compile and render through the
  new theme.
- Maps to DoD criteria 29, 30, 31 (partial — the reachability half of 31 is proven by `assembleDebug`, not
  by this task alone).
