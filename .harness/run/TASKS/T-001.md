## Description

The first time the app is brought to the foreground on a given calendar day (cold launch or resume from
background), it posts a notification with a friendly greeting. Every later foreground on the same day
posts nothing. A new calendar day re-arms it automatically.

**Architecture decisions already made for you — implement them, do not re-derive them:**

1. **Foreground signal:** override `onStart()` in `MainActivity.kt`. Not `ProcessLifecycleOwner` —
   `androidx.lifecycle:lifecycle-process` is not a dependency this app has, and the PRD forbids adding
   one. `onStart()` fires on cold launch, on resume from background, and also on every configuration
   recreation (rotation, this app's in-app language picker) — that is fine as long as the check-and-write
   sequence below is safe to call repeatedly and concurrently.
2. **Testable seam (Constraint C-06):** write the once-per-day decision as a plain Kotlin function in
   `domain/greeting/GreetingDecision.kt`, taking today's date and the stored last-greeted date, with no
   Android type in its signature — the same shape as `domain/scheduler/NextFireTime.kt`. Compare by
   **calendar day** via a `java.time.Clock` you can fix in a test (23:58 and 00:02 the next day are two
   different days). `GreetingNotifier` and `MainActivity` are the only places that ever touch a real
   clock or the framework notification APIs; nothing there is unit-testable (they are silent stubs under
   this toolchain), so all the interesting logic must live in the pure function.
3. **Persistence:** add a key to `SettingDatastore` for the last-greeted date (a `stringPreferencesKey`
   storing `LocalDate.toString()` — ISO-8601 — follows the existing pattern of string-backed keys there).
   Expose it through `SettingRepository`/`SettingRepositoryImpl` the same pass-through way every other
   field there works. Do not hold the fact in a `var`, companion object, or any in-memory field — it must
   survive process death.
4. **Concurrency:** `GreetingNotifier`'s check-and-write sequence (read the stored date, decide, notify,
   write the new date) must be guarded by one `Mutex`, named for what it guards, per this codebase's
   one-mutex-per-concern convention (see `.harness/knowledge/PROJECT.md` § Architecture Conventions,
   "Concurrency"). Without it, two `onStart()` calls close together (e.g. a rotation) could both read
   "not yet greeted" before either writes, and both post.
5. **Notification channel:** its own channel, id `"greeting"`, `NotificationManager.IMPORTANCE_DEFAULT`
   — not the alarms channel (`AlarmNotifier.CHANNEL_ID`), and never renamed later (Constraint C-10: a
   channel's importance is frozen forever the first time it is created on a real device). Mirror
   `AlarmNotifier.kt`'s shape: a `createChannelIfNeeded()` you expose for the Iteration to call from
   `MainApplication.onCreate` (you do not edit that file yourself — see Not in scope above), constants in
   a bottom `companion object` (channel id, importance, and anything else worth a
   `GreetingNotifierConstantsTest` mirroring `AlarmNotifierConstantsTest`), a small icon that is not the
   launcher mipmap (reuse `R.drawable.ic_notification_alarm` unless you have a good reason for a new one
   — say which and why if you add one), and the same `try/catch (SecurityException)` +
   `NotificationManagerCompat.from(context).notify(...)` shape for the post itself. Write the persisted
   date regardless of whether the notify call actually succeeded — this app's existing pattern treats
   "tell the user permission is missing" as the permission notice's job, not the notifier's, and the
   PRD's "once per day" is about the calendar day, not about retrying until permission is granted.
6. **Wiring:** bind `GreetingNotifier` in a new `injection/NotificationModule.kt` (do not fold it into
   `injection/SchedulerModule.kt` — that module's own KDoc scopes it to the alarm-scheduling seam).
   `MainActivity` reaches it via `by inject()` (Koin's Android extension), the same way any other
   Android-instantiated class in this app reaches Koin.
7. **Greeting text** is a `strings.xml` key, never a literal — you do not edit `strings.xml` yourself
   (Constraint C-02); report the key name and its English + German text in your final report.
