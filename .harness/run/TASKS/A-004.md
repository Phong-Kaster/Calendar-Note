## Description

This is the task the addendum was actually about, and it is the one whose central promise no command in
this repository can check. The whole design exists to make as much of it machine-provable as possible.

**The seam.** `AlarmScheduler` is an **interface in `domain/`** — `fun schedule(alarm: Alarm)`,
`fun cancel(alarmId: Long)` — with `AlarmManagerAlarmScheduler` in `data/` behind it. This is a requirement
of the plan, not a style preference: `AlarmManager`, `PendingIntent` and `NotificationManager` all return
silent stubs under this repository's JVM test toolchain (C-06), so a test whose *subject* is one of those
types passes vacuously. With the seam, the arithmetic, the arming and the cancelling become plain unit
tests and only "did the OS deliver it, and did it look like a popup" is left for a person.

**The arithmetic is a pure function behind an injected `Clock`.** `NextFireTime.kt` holds a plain Kotlin
function — no Android types — taking `hourOfDay`, `minute` and a `Clock`. `java.time` is safe here despite
`minSdk = 24` because core library desugaring is on. Cases criterion 19 requires, each its own test: later
today → today; earlier today → tomorrow; **exactly now → assert which side of the boundary you chose**, and
say so in a comment (an off-by-one here either double-fires or skips a day); 00:00 when now is 23:59 → one
minute away and tomorrow's date; a rollover across a month boundary; and the occurrence after a firing at T
is exactly T + one day at the same wall-clock time.

**Mirroring belongs in the repository, not in the ViewModels.** `AlarmRepositoryImpl` takes
`alarmScheduler: AlarmScheduler` and mirrors every mutation: save an enabled alarm → arm exactly one
schedule at the expected instant; save over an existing id → cancel the old, then arm the new; delete →
cancel; set `enabled = false` → cancel; set `enabled = true` → arm **from the current clock reading**, which
is the second half of criterion 29. Putting it here rather than in three ViewModels is what makes it
impossible for a caller to bypass. **A delete that removes the row and leaves the schedule pending is the
worst defect this feature can have** — it notifies for an alarm the user deleted. Test it with a
hand-written `FakeAlarmScheduler` recording calls.

**Two notification paths, and only one of them is obvious (C-10).** Set the channel to `IMPORTANCE_HIGH`
**and** the builder to `NotificationCompat.PRIORITY_HIGH` with a sound or vibration. On API 24–25 there are
no channels at all and the builder path is the only one; setting only the channel leaves the PRD's central
ask unmet on two API levels with a fully green build. A channel's importance is **immutable once created** —
get it right the first time or ship a new channel id. Category `CATEGORY_ALARM`, title is the app name,
body is the user's message (AS-7, AS-10). **No full-screen intent and no DND override**: "popup" is read as
heads-up, not an alarm-clock takeover.

`setSmallIcon` takes `ic_notification_alarm` — a real notification icon, **never `@mipmap/ic_launcher`**,
which renders as a white blob. Copy the 24dp vector shape from an existing `ic_bottom_*.xml`.

**Assert your own constants, not the framework's objects.** A `NotificationChannel` constructed on the JVM
is a stub whose getters return `0` (C-06), so asserting on the object is a tautology. Expose the importance,
the priority, the category and the channel id as constants and assert on those.

**Exact, but not `USE_EXACT_ALARM` (AS-9).** `setExactAndAllowWhileIdle`, re-armed on each firing from
`AlarmReceiver`, using the already-declared `SCHEDULE_EXACT_ALARM`. Where the permission is absent, fall
back to an inexact window rather than throwing — the telling-the-user half is A-006.

**The request code is `id.toInt()`** — A-002 decided this and the schema depends on it. If it turns out
wrong, stop and report: that is a Tier-1 amendment and a second migration, not a silent schema change.

**The Iteration handles, and you must not touch:** `AndroidManifest.xml` (the `<receiver>`, `MainActivity`'s
`launchMode`), a new `injection/SchedulerModule.kt` plus its entry in `AppModule.kt`'s `includes`,
`RepositoryModule.kt` (the new constructor argument), `MainApplication.kt` (channel creation at startup),
`MainActivity.kt` (opening on the Alarms list from the notification, AS-6), both `strings.xml`, `README.md`.

**Report, do not write:** every new string key with English and German text; the exact `<receiver>` element
you need in the manifest; the exact Koin definitions you need.
