## Description

Android drops **every** scheduled alarm on restart. Without a boot receiver this fails silently and there
is no way to notice except by rebooting a phone and waiting — which is exactly why it is its own task
rather than a line in A-004.

Add `rearmAll()` to the `AlarmScheduler` interface: read every enabled alarm out of the store and arm each
one from the current clock reading. It must use the same next-fire arithmetic A-004 wrote — an alarm whose
time already passed today arms for tomorrow, not for a moment in the past.

`BootReceiver` is a `BroadcastReceiver` handling `ACTION_BOOT_COMPLETED`. `onReceive` runs on the main
thread with a short budget and the store read suspends, so take a `goAsync()` pending result and release it
in the coroutine's `finally` — releasing it exactly once, on every path including failure. Resolve the
scheduler through Koin at the receiver rather than through a constructor; a `BroadcastReceiver` is
instantiated by the framework and cannot be given one.

**Do not write a test whose subject is a `BroadcastReceiver`, an `Intent` or a `PendingIntent`** — under
this repository's toolchain every unmocked framework call returns `0`/`false`/`null` silently and the
assertion passes vacuously (C-06). `RearmAllTest` tests `rearmAll`'s *decision* over a fake store and a
fake arming sink with a fixed `Clock`: enabled alarms are armed, disabled ones are not, and one whose time
has passed today is armed for tomorrow. That is the whole machine-checkable part; the rest is criterion 32
and needs a person with a phone.

**The Iteration handles, and you must not touch:** `AndroidManifest.xml` (`RECEIVE_BOOT_COMPLETED` and the
boot `<receiver>` with its `<intent-filter>`), `injection/SchedulerModule.kt`, both `strings.xml`,
`README.md`.

**Report, do not write:** the exact `<uses-permission>` and `<receiver>` elements you need.

**You share Phase 5 with A-006.** It lives entirely in `ui/fragment/alarms/`. You must not read or write
anything there — and in particular, **do not** expose scheduler state for it to query. That disjointness is
what makes the two safe to run at once.

## Notes

- A boot receiver that throws takes the boot broadcast down with it. Every path inside `onReceive` is
  wrapped and fail-soft; a store that cannot be read logs and returns, it does not propagate.
- `RECEIVE_BOOT_COMPLETED` is a normal permission — no runtime request, but the receiver must be
  `exported="true"` to hear the system broadcast at all, which is the one place in this feature where
  `exported` is not `false`.
- A Fresh-Context Review found that granting the exact-alarm permission back after a refusal needs the
  same `rearmAll` this task built — see A-006's Evidence and `AMENDMENTS.md` A-14 #1. That wiring lives
  in `AlarmsViewModel`, not here, but it is the reason this task's `rearmAll` exists as a public seam on
  the interface rather than something `BootReceiver` alone could have owned privately.
