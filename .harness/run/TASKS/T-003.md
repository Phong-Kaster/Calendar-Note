## Origin

Human verification of DoD criterion 15 (D-002, 2026-09-15) came back **FAIL**. With app data cleared,
the user opened the app, granted the notification permission when asked, closed it and opened it
again — and no greeting ever appeared, on the day of the install or afterwards.

Cause, confirmed in the source: `GreetingNotifier.greetOnceToday()` writes the greeted date whether or
not the greeting reached the user. `NotificationManagerCompat.notify()` on Android 13+ **silently
posts nothing** when `POST_NOTIFICATIONS` has not been granted — it does not throw — so on a fresh
install, where the first `onStart()` runs before the user has been asked for the permission, the date
is written against a greeting nobody saw. `greetingDueOn` then answers `null` for the rest of that day
and the user is never greeted on the day they installed the app.

## Description

Record the greeted date **only when the system accepted the greeting for display**. A greeting that
went nowhere leaves nothing written down, so the next foreground that day tries again.

### The delivery rule — implement exactly this

"Delivered" means: **the app is allowed to show notifications, and the post did not throw.**

- Before building the notification, ask
  `NotificationManagerCompat.from(context).areNotificationsEnabled()`. `false` → **not delivered**;
  do not post, do not record. This one call covers both cases that matter: `POST_NOTIFICATIONS` not
  granted on API 33+, and the user having turned this app's notifications off entirely.
- A `SecurityException` out of `notify(...)` → **not delivered**; do not record.
- Otherwise → **delivered**; record the date.

**The user who switched the greeting channel off on purpose is deliberately counted as delivered.**
`areNotificationsEnabled()` stays `true` when only one channel is muted, so the post is a silent no-op
and the date is written. That is the intended behaviour, not an oversight: that user made a choice
about *this* notification, and honouring it means the app stops asking. The user who has not yet been
asked for the permission has made no such choice, which is exactly why the two are treated differently.
Say this in the KDoc, because the next reader will wonder.

### The seam — Constraint C-06 and DoD constraint K-3

`NotificationManager` and `NotificationManagerCompat` are silent stubs under this toolchain, so a test
whose subject is either of them is not evidence. Pull the whole sequence out into plain Kotlin:

Create `domain/greeting/GreetOnceADay.kt` — Android-free, `kotlinx.coroutines` only, the same shape as
`domain/scheduler/NextFireTime.kt` and the existing `GreetingDecision.kt` next to it:

```kotlin
suspend fun greetOnceADay(
    lastGreetedDate: LocalDate?,
    clock: Clock,
    postGreeting: suspend () -> Boolean,      // true when the system accepted it for display
    recordGreetedOn: suspend (LocalDate) -> Unit,
)
```

It asks the existing `greetingDueOn(...)` whether a greeting is due, returns when it is not, and
otherwise posts and — **only on `true`** — records. Keep the `withContext(NonCancellable)` around the
post-and-record pair and keep its reasoning: a rotation cancelling the scope between the two would
greet the user without remembering it. Adapt the existing comment rather than deleting it.

`GreetingNotifier` then becomes the thin Android arm: same public `greetIfFirstForegroundToday()`, same
`greetingMutex` guarding the whole sequence, same `CancellationException` re-throw and same
catch-and-log around it. `postGreeting()` changes from `private fun` to `private fun ... : Boolean`.

### Same-day recovery after the grant

`HomeFragment` already calls `HomeRequestPermission(onNotificationGranted = { /* empty */ })`. Wire
that empty hook to `greetingNotifier.greetIfFirstForegroundToday()` so the greeting arrives the moment
the user grants the permission, instead of only on their next app open. Reach `GreetingNotifier`
through Koin (`private val greetingNotifier: GreetingNotifier by inject()`, the
`org.koin.android.ext.android.inject` import — `MainActivity.kt` is the worked example), never by
constructing one: the `Mutex` that stops two greetings going out at once lives inside the single
instance. Launch it on the fragment's own coroutine scope; do not block the callback.

That callback fires on every composition where the permission reads granted, not only on the
transition. That is safe and is the point: `greetIfFirstForegroundToday()` advertises itself as safe to
call on every foreground and answers "already done today" itself.

## Acceptance Criteria

1. `GreetingNotifier` writes the greeted date on no path where the greeting was not delivered, by the
   rule above. The `areNotificationsEnabled()` check is present and precedes the post.
2. The decision sequence lives in `domain/greeting/GreetOnceADay.kt` with no Android type in its
   signature, and `GreetingNotifier` delegates to it rather than repeating it.
3. `GreetOnceADayTest` proves, over fakes and a fixed `Clock`, at least:
   - never greeted + delivery succeeds → posts once, records today;
   - never greeted + delivery **fails** → nothing is recorded;
   - already greeted today → does not post at all, records nothing;
   - **failure then success on the same day → the date is recorded only on the success, and exactly
     one greeting goes out** (this is criterion 15's regression, written as a test);
   - success then a second call the same day → still exactly one greeting (T-001's promise survives).
4. `HomeFragment`'s `onNotificationGranted` asks the injected `GreetingNotifier` for the greeting.
5. Public behaviour otherwise unchanged: one greeting per calendar day, `greetingMutex` still guards
   the whole read-decide-post-write, `CancellationException` still re-thrown, nothing else throws out
   of `greetIfFirstForegroundToday()`.
6. No new string, no new dependency, no edit to `libs.versions.toml` or `app/build.gradle.kts`.
