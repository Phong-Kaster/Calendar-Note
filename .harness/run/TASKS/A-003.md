## Description

Three behaviours the addendum never asked for and that AS-2, AS-3 and AS-4 commit to. All three land
together because each one rewrites `AlarmRow` and `AlarmsViewModel`, and splitting them would put two
Workers in one file.

**Re-open and change (AS-2).** Tapping a row opens `AlarmEditorFragment` with that alarm's id. Follow
`NoteFragment.argumentsFor(...)`: the key strings live in one `companion object` factory on the destination
Fragment, every `<argument>` in the graph gets a `defaultValue`, and the "no alarm yet" sentinel is `-1L`
— **not `0`**, which is Room's autogenerate marker (C-08). The editor ViewModel loads by id on init and
saves back to the same row; `@Insert(onConflict = REPLACE)` makes that an update, so the row count must not
change. Debounce the row tap by asking the graph where you are
(`findNavController().currentDestination?.id == R.id.alarmsFragment`) — **never `NavigationUtil.canNavigate()`**,
which is one process-wide 800 ms window that kills every other control in the app (C-07).

**The confirmation is state, not a dialog you can bypass (AS-3).** Put `pendingDeleteId: Long?` (or an
equivalent nullable field) on `AlarmsUiState`. `askToDelete(id)` only sets it and touches no store;
`confirmDelete()` is the only path that calls the repository and it returns early when nothing is pending.
That shape is what makes criterion 26 a unit test rather than something only a person can check.
`AlarmDeleteConfirmSheet` renders it: the destructive action **filled in `colorScheme.error` with bold
text**, the way out **unfilled plain text** — differing in colour role *and* emphasis, because on a black
ground two buttons differing only in hue are a coin toss (DoD 28).

**Delete must report matching nothing.** `AlarmDao.delete` returns `Int` and the impl turns `0` into an
`Outcome.Error` (C-09). Without the count the screen announces a deletion that never happened.

**Switch off without deleting (AS-4).** A per-row `Switch` writing `enabled` through the repository. The
column already exists — A-002 shipped it. The switch's thumb must be clearly distinct from its track
(DoD 30): read both from the theme, and check the pair against the surface the row is drawn on rather than
judging the swatch (C-01, and the `outline`-at-2.19:1 precedent in PROJECT.md).

**Every `Text` uses `customizedTextStyle(...)`, never `MaterialTheme.typography` (C-11).** Format the time
against `LocalConfiguration.current.locales[0]`, never `Locale.getDefault()` — the app has its own language
picker — and wrap the formatter in `remember(locale) { … }`.

**The Iteration handles, and you must not touch:** both `strings.xml` files, `AlarmsScreenshotTest.kt`,
`navigation_graph.xml`, `README.md`.

**Report, do not write:** every new string key with its English text and a German translation.

## Acceptance

The user can tap an alarm to change it, flip it off and on, and delete it only after saying yes twice.

- DoD 24 — re-opening loads stored values; saving updates the row instead of adding one
- DoD 26 — the confirmation step is unconditional; asking to delete leaves the store untouched
- DoD 27 — deleting removes the record; a delete matching no row is an `Outcome.Error`
- DoD 25, 28, 30 — the row opens pre-filled; the delete control is findable and its confirming button is
  unmistakable; the switch reads correctly at a glance *(human)*
- DoD 29 — **the persistence half only.** "Switching on schedules from the *current* time" needs the
  scheduler and completes in A-004. Do not claim criterion 29 here.
- DoD 33, 34 — no hardcoded colour, no hardcoded string
- A `@PreviewTest` case for the confirmation sheet and for a row in both switch states, sized per C-05

## Notes

- `delete`, `cancel`, `save` already exist as string keys (PROJECT.md § Strings). Reuse them rather than
