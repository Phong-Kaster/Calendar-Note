## Description

The whole persistence vertical plus the editor screen, in one checkpoint because no part of it is
demonstrable alone: splitting at the persistence boundary leaves one half with no caller.

**Schema, decided now and final.** `AlarmEntity` carries: `id` (autogenerate `Long`), `message` (`String`),
`hourOfDay` (`Int` 0–23), `minute` (`Int` 0–59), `enabled` (`Boolean`, default `true`), `createdAt`
(`Long`). Store the time as two `Int`s rather than through a converter — the same reasoning that made
`NoteEntity` store an epoch day as a raw `Long`: it keeps comparisons integer and confines the conversion to
`AlarmMapper.kt`.

**Why `enabled` ships now even though nothing reads it until A-004:** a second hand-written migration is the
most dangerous operation available in this repository (C-03) and paying that risk twice for one column is a
bad trade. It is dead weight for two Phases, deliberately.

**Scheduler data requirements, sketched now so the schema really is final** (PLAN.md risk 4): the scheduler
derives its `PendingIntent` request code from `id.toInt()`. Row ids here are sequential from 1, so the
truncation is safe and no separate request-code column is needed. No `lastFiredAt` is needed either — the
next fire time is computed from `hourOfDay`/`minute` against the injected `Clock`, never from history.
**If A-004 finds either of these wrong, that is a Tier-1 amendment and a second migration, not a silent
schema change.**

`AlarmRepository` follows `NoteRepository`: a non-suspend `val alarmsFlow: Flow<List<Alarm>>` doing the
time-ascending sort **in the repository, not in SQL**; `suspend fun getAlarm(id): Outcome<Alarm?>` (three
answers, so `Outcome<T?>` — C-09); `suspend fun save(alarm): Outcome<Unit>`. Take
`clock: Clock = Clock.systemDefaultZone()` and `ioDispatcher` as constructor parameters. A blank message is
refused as `Outcome.Error(throwable = BlankAlarmMessageException(...))` — tagged by type, never by message
text.

The editor screen is a Fragment (`alarm_editor/`), reached by a FAB on the Alarms screen — fill
`CoreLayout`'s existing `floatingActionButton` slot with a Material `FloatingActionButton` using
`containerColor = colorScheme.primaryContainer` / `contentColor = colorScheme.onPrimaryContainer`, which is
the contrast-verified pair (9.12:1). Give the list bottom `contentPadding` of at least the FAB's height plus
twice its margin, as a named constant, so the last row is never covered.

**The message field needs `Modifier.imePadding()` before `verticalScroll` (C-04)** — this is a full-screen
text input and the window is never resized when the keyboard opens.

Tests: hand-written `FakeAlarmDao` (returning a **jumbled** list, so the repository's own sort is what is
under test) and a `BrokenAlarmDao` failing every call to reach the catch blocks. ViewModel tests via
`Dispatchers.setMain(UnconfinedTestDispatcher())`. Do **not** write a test whose subject is a `Bundle` (C-06).

**The Iteration handles, and you must not touch:** `AppDatabase.kt` (entity list, `version = 4`,
`alarmDao()`), `Migration.kt` (`MIGRATION_3_4`, whose SQL it copies out of the generated
`AppDatabase_Impl.kt` after building your entity), `DatabaseModule.kt`, `RepositoryModule.kt`,
`ViewModelModule.kt`, `navigation_graph.xml`, both `strings.xml`, `AlarmsScreenshotTest.kt`, `README.md`.
