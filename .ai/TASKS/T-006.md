# T-006 — Calendar screen: month grid, today marked, month navigation, future days inert

- **Status:** pending
- **Depends on:** T-002, T-010
- **Attempts:** 0 / 3

## Description

Add the Calendar screen and get the month grid right before hanging any note behaviour off it.

- New screen `ui/fragment/calendar/` — `CalendarFragment`, `CalendarUiState`, `CalendarViewModel`,
  private `CalendarLayout` + `@Preview`s for the meaningful states. Reachable from the app's
  navigation: add the destination and action to `res/navigation/navigation_graph.xml` and an entry
  point (extend `BottomBarDestination` / `CoreBottomBar`, matching how Home and Setting are wired).
- Month grid for the displayed month, with weekday headers and correct leading/trailing blanks.
  Previous / next month controls.
- **The day-cell state is plain Kotlin, not a composable.** Put the mapping
  `(date, today, displayedMonth) -> DayCellState` (`Past`, `Today`, `Future`, `OutsideMonth`) in a
  testable place — `CalendarUiState` as a derived value, or a small domain helper. A rule that lives
  inside `@Composable` can only be checked by rendering it, and this repository cannot render in a
  test.
- Every day after today renders visibly disabled and ignores taps: no `clickable`, or a `clickable`
  whose `enabled` is false — not a click handler that silently does nothing, which is
  indistinguishable from a bug.
- Today is marked. Selection is marked. Check the **combined** states, not each alone: today *and*
  selected, selected *and* has-notes. A marker that repeats the fill it sits on is invisible
  (`POLICIES.md` § User-Interface Defects).
- All colours from the theme built in T-001.

## Acceptance

- A unit test proves the grid for a known month has the right number of leading blanks and the right

- The diff shows no tap handler reachable for a `Future` cell.

  today+selected, selected+hasNotes, plain+hasNotes, a future/disabled cell, and the full month grid.

  fill underneath is judged by eye on first sight, and defended by the machine thereafter.

## Notes

### Three regressions a prior run already shipped here — read before writing the grid

`loop/todo-calendar-screens` built this same screen once. Its screenshot suite names exactly what
went wrong, and **the unit suite was green for all three**. Read the file first:
`git show loop/todo-calendar-screens:app/src/screenshotTest/kotlin/com/example/skeleton/screenshot/CalendarScreenshotTest.kt`

1. **A has-notes dot drawn in `primary` on top of a `primary`-filled today cell — invisible**, on
   exactly the day a user looks at first. A test can assert the date is in `datesWithNotes`; it
   cannot see that the marker vanished.
2. **Selection never reached the grid** — `selectedDate` was computed and never passed down.
3. **A selected day with no notes rendered an unexplained blank gap** (that one lands in T-007).

Write the screenshot cases with the grid, using the harness imported in T-010 and the prior file as
the pattern — at minimum: today+hasNotes, today+selected, selected+hasNotes, plain+hasNotes, and the
full month grid. These are the combinations, not the individual states, and the combinations are
where it broke.

### Other

- `java.time` is available on `minSdk 24` through core-library desugaring (already enabled). Use
  `LocalDate`, `YearMonth` and `DayOfWeek` rather than `Calendar`.
- The week start day is locale-dependent. Pick one deliberately and say which in the KDoc — a grid
  that assumes Monday on a locale that starts on Sunday is off by one for every cell. **The prior run
  chose Sunday-first**, and its screenshot suite pins the weekday header against the grid for that
  reason. Match it unless there is a reason not to, and say which you chose.
- Do not import a third-party calendar library. That would be a technology choice, i.e. Tier 2, and
  needs an escalation first.
- **Draw day-cell boundaries from `outline`, not `outlineVariant`.** T-001 set them up as a
  deliberate pair: `outline` (`#55616E`) clears 3:1 against the black ground and is for edges that
  carry meaning; `outlineVariant` (`#232B34`) is intentionally near-invisible and is for decorative
  dividers only. `outline` itself was caught at 2.19:1 during T-001 and raised — on pure black a
  too-dark border does not read as subtle, it reads as absent, and a grid with no visible cell edges
  is the kind of thing every automated check passes.
