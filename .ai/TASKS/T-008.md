# T-008 — Add a note to the selected day; the repository refuses future-dated notes

- **Status:** pending
- **Depends on:** T-007, T-003
- **Attempts:** 0 / 3

## Description

The PRD's one explicit business rule, enforced where a second caller cannot walk past it.

> **The rule itself already landed, in T-003 (amendment A-006).** `NoteRepositoryImpl.save` refuses
> any note dated after `LocalDate.now(clock)` and returns `Outcome.Error`, on every write path
> including edit, with today inclusive — and **DoD criterion 10's test exists and was
> mutation-checked**. The reason it moved: `DOMAIN.md` puts the enforcement point in the repository
> so no caller can bypass it, and T-003 is where the first write path exists, so leaving `save`
> permissive would have been checkpointing code known to contradict a human-owned rule.
>
> **This task is now the second caller reaching that guard, plus the calendar half.** Do not
> re-implement the rule. Do re-verify it from this caller — a second route to the same guard is
> worth its own test, and this is the route that makes a refusal reachable by ordinary use.
> Read `.ai/TASKS/T-003.md` first.

- The Calendar screen offers an add-note action for the selected day, which navigates to the Note
  screen with **that day's** date (not today) through the existing `toNote` route from T-003.
- No add affordance is offered when the selection is a future day — which cannot happen, since T-006
  made future cells inert, but the action must not assume it.
- **`NoteRepository` refuses to save a note whose date is after today** and reports the refusal to
  its caller without throwing (`Outcome.Error`, per `.claude/repository-layer.md`: repositories never
  throw across the boundary). The rule lives in the repository, not in the calendar cell — a rule
  enforced only in a grid cell is a rule the next caller walks past.
- **This rule is now in `knowledge/DOMAIN.md`** (created by the human through escalation D-001), so
  it outranks the codebase: any difference is a defect in the code, never a reason to amend the rule.
  Implement it exactly as written there, including the parts this task summarises loosely:
  - it applies to **every write path — create and edit alike**. The check belongs on the single
    `save` the repository exposes, so both routes pass through it; if create and edit ever take
    different paths, both get the check.
  - the boundary is **inclusive of today**: today allowed, tomorrow refused.
  - the refusal is a returned value, never a thrown exception.
- **The refusal is surfaced to the user rather than swallowed, and this part is genuinely unfinished
  work for this task.** Today the editor shows the same `we_are_sorry` toast ("something went wrong,
  please try again") for a refusal as for a disk failure — and retrying a refusal can never succeed,
  while the editor offers no date control to change what was refused. That is survivable while the
  only reachable refusal needs the device clock to move backwards; it stops being survivable here,
  because this task is what lets a user pick the day. Distinguish refusal from failure in the
  outcome and give the refusal its own message naming the day. Filed as
  `knowledge/ISSUES.md` § *Leaving the Note editor either loses the user's text or traps them on the
  screen*, part 2 — resolve it here and delete that part of the entry.
- "After today" is evaluated against the device's local date. State the timezone assumption in the
  KDoc.
