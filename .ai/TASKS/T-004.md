# T-004 — User can open and edit an existing note; Home re-sorts

- **Status:** pending
- **Depends on:** T-003
- **Attempts:** 0 / 3

## Description

Close the read-modify-write loop.

- Tapping a row on Home navigates to `NoteFragment` with that note's id; `NoteViewModel` loads it and
  seeds **both** editor fields — title and body — with its stored values (amendment A-001).
- Saving an edit updates the row in place (same `id`, same `createdAt`, same `date`) and sets
  `updatedAt` to now. A title edited to blank stays blank and falls back to the first body line for
  display; it does not resurrect the old title.
- Home reflects both the new text and the note's new position at the top of the list, because the
  list is ordered by `updatedAt` descending and is driven by a `Flow` — no manual refresh.
- Give the Note screen a back affordance that does not lose the edit silently. Either save on
  navigate-back or make the save action explicit and obvious; pick one and state it in the KDoc.

## Acceptance

Maps to DoD criterion 6.

- Build, unit tests and lint succeed.
- A unit test proves: updating an existing note keeps its `id`, `createdAt` and `date`, advances
  `updatedAt`, and moves it to the head of the ordered list.
- A unit test proves an edit that blanks the title persists the blank and the display label falls
  back to the first body line.
- Recorded as **needing human inspection** (class (I) until host-side UI tests exist): tapping a row
  opens that note's text, editing and saving shows the change on Home.

## Notes

- The reordering assertion is the one that catches an accidental `ORDER BY createdAt` — write it
  against a note that is old by creation and new by edit, or it proves nothing.
- Watch the "new note" sentinel: id `-1L` must not be able to reach `getById`.
- `knowledge/DOMAIN.md` rule 2 governs the ordering here and rule 1 governs the write: an edit must
  leave `createdAt` alone and advance `updatedAt`, and an edit is a write path like any other, so it
  passes through the same `save` that T-008 puts the future-date check on. This task keeps a note's
  `date` unchanged, so it cannot violate rule 1 — but do not add a date-editing affordance here
  without routing it through that check.
