# T-004 — User can open and edit an existing note; Home re-sorts

- **Status:** ✅ complete

## Description

Close the read-modify-write loop.

> **Reduced by amendment A-007 (iteration 5).** The machinery this task was going to build already
> exists: `NoteRepository.getNote(id)`, `NoteViewModel.openNote(noteId, date)` loading a stored note,
> the `noteId` nav argument, and a `save` that preserves `id` and `createdAt`. All of it landed in
> T-003, where the stamping logic was written, and all of it is unit-tested there — including the
> `createdAt`-clobbering trap, which is invisible on a fresh database.
> **What is left for this task is what makes editing observable: the route in.** Read
> `.ai/TASKS/T-003.md` before starting; do not rebuild any of the above.

- Tapping a row on Home navigates to `NoteFragment` with that note's id, through the existing
  `R.id.toNote` action and `NoteFragment.argumentsFor(date = note.date, noteId = note.id)`. The rows
  are drawn by `HomeNoteList`'s private `NoteRow`, so the click callback has to come down from
  `HomeFragment` through `HomeNoteList`.
- Confirm — do not re-implement — that the editor seeds **both** fields from the stored note and
  that saving updates the row in place (same `id`, same `createdAt`, same `date`) with `updatedAt`
  advanced. A title edited to blank stays blank and falls back to the first body line for display;
  it does not resurrect the old title. **That last clause is genuinely new work**: nothing tests a
  blanked title yet.
- Home reflects both the new text and the note's new position at the top of the list, because the
  list is ordered by `updatedAt` descending and is driven by a `Flow` — no manual refresh.
- The back affordance question this task used to own is now an open issue rather than a blank
  cheque: see `knowledge/ISSUES.md` § *Leaving the Note editor either loses the user's text or traps
  them on the screen*. The editor currently discards silently on back. Deciding otherwise is a
  product decision — resolve it, or state here why it stays as it is.

### The back-affordance decision: it stays as it is, and here is why

`knowledge/ISSUES.md` § *Leaving the Note editor either loses the user's text or traps them on the
screen* stays open, deliberately.

- **Part 1 (nothing is saved on the way out) is a product decision, not an implementation gap.**
  Confirm-on-discard, save-on-leave, and "notes are kept only when you tap Save" are three different
  products with three different failure modes — autosave in particular manufactures empty notes that
  nobody wrote and puts them at the top of a list sorted by recency. No DoD criterion asks for any
  of them. Choosing on the human's behalf is exactly what `POLICIES.md` § Reconciliation Rules
  forbids.
- **But this task made part 1 worse in kind, and that is recorded.** Before this checkpoint the only
  text a back gesture could destroy belonged to a note that had never existed anywhere, so "I never
  saved it" matched what the user saw. Now a discarded *edit* returns the user to Home showing the
  note with its old text, its old position and its `updatedAt` unmoved — a screen indistinguishable
  from a save that quietly did nothing. The `ISSUES.md` entry has been amended to say so; its
  original wording described only the create case.
- **Part 2 (a refused save has no way forward) is *not* newly reachable here**, which was worth
  checking rather than assuming: an existing note's date is always today or earlier, so re-saving
  one can never trip the future-date rule. It stays scheduled for T-008, where a day picked on the
  calendar makes a refusal reachable by ordinary use.

## Fresh-Context Review

Reviewer given the staged diff, the task, `DoD.md`, `POLICIES.md`, `DOMAIN.md`, the house rule files
and `knowledge/`, and **not** given any implementation reasoning. 6 findings, 0 Critical.

**3 Major, all three resolved — one fixed, two filed with a schedule:**

1. **A note row's tap was silently swallowed for 800 ms after any bottom-bar tap.** Fixed in this
   iteration. `NavigationUtil.canNavigate()` is not per-control — it reads and writes one
   process-wide `lastNavTime`, and `CoreBottomBar.BottomBarElement` consumes it *before* checking
   whether the tab tap navigates anywhere, so tapping "Home" while already on Home armed the window
   and left every note row dead for the next 800 ms. Ripple, no navigation, no explanation. The
   reviewer's own summary of the diff's KDoc was the sharpest version of the point: the row claimed
   to exist so that taps would not be ignored. Replaced with a question about *where we are* —
   `findNavController().currentDestination?.id == R.id.homeFragment` — which has no dead window at
   all, because `navigate` moves `currentDestination` immediately, so the second tap of a double tap
   is already standing on the editor and is refused. `launchSingleTop` was considered and rejected:
   it reuses the `NoteFragment`, `onCreate` does not re-run, and `openNote` short-circuits on
   `opened`, so the second tap would leave the *previous* note on screen.
2. **A failed read on the way in converts an edit into a second note.** Filed, and made a
   prerequisite of **T-005**. `getNote` answers `null` both for "no such row" and for "the read
   threw", and `openNote` treats `null` as "start a new note" — so the editor opens blank but
   correctly dated, and the save inserts, because the draft carries `UNSAVED_ID`. Home then shows
   two notes for that day: the original with its old text, plus the retyped copy. **This task is
   what made the branch reachable** (before it, every caller of `argumentsFor` left `noteId` at its
   default, so `getNote` had no in-app caller at all), and it becomes ordinary at T-005, when delete
   means "the note you opened is gone" no longer requires a disk fault. Not fixed here because the
   clean fix distinguishes refusal from failure in `getNote`'s return type and overturns a
   deliberate, tested, documented T-003 decision — `NoteViewModelTest`'s *a note that has since been
   deleted opens as a fresh one for the day asked for* pins the current behaviour on purpose. That is
   a Major, and `POLICIES.md` says a Major is filed. → `knowledge/ISSUES.md`, plus a required
   acceptance criterion in `.ai/TASKS/T-005.md`.
3. **The back-affordance decision this task file required was not stated, and the open issue got
   worse in kind.** Resolved by stating it — see *The back-affordance decision* above — and by
   amending the `ISSUES.md` entry, whose wording covered only the create case. The reviewer also
   checked and refuted the adjacent worry: part 2 of that entry is *not* newly reachable.

**3 Minor, all three fixed:**

4. **One assertion in the new reordering test could not fail.** `assertEquals(TODAY, ...)` against a
   fixture that used the helper's default `date = TODAY.toEpochDay()`, with `CLOCK` fixed to the same
   day — so the assertion read as a guard against an edit re-filing a note onto today while being
   incapable of catching it. The fixture is now dated three days back and the mutation table above
   has a row proving the assertion bites. **The general lesson is sharper than the fix:** mutating
   the implementation once per *test* is not enough, because a test can fail for one reason while
   another of its assertions is dead. This one survived three mutations before a reader found it.
5. **`HomeScreenshotTest.kt` carried a promise this task was the designated place to keep** — "[the
   `Untitled note` fallback] arrives with the rows, when they become clickable". The rows became
   clickable here and no populated-row case was added. The sentence is now the honest version: what
   is still unpinned, why, and what `@Preview(locale = "en")` would and would not buy.
6. **KDoc verbosity in the changed composable.** A five-line `@param` and two multi-line comments
   inside a six-modifier chain, against a house rule that caps KDoc at a two-second read. Rationale
   moved into the function KDoc body (matching `CoreBottomBar`), `@param` cut to one line.

Also verified by the reviewer and worth recording as *not* defects, since each was a plausible

## Notes

- **The house-rule call worth flagging:** `HomeNoteList.onOpenNote` has **no default**, which
  `.claude/figma-design-system.md` requires of an `XxxLayout` and does not require of a component.
  `HomeLayout.onOpenNote` keeps its `= {}` as the rule demands; the component follows
  `CoreBottomBar.onCreateNote`'s precedent instead, because a row that draws a *truncated* note and
  does nothing when tapped leaves the rest of the text unreachable and looks exactly like a working
  screen. It cost one line in `HomeScreenshotTest.kt` and two in the previews.
- **Carried forward, unchanged from T-003:** `NoteDao.upsert` returns the generated row id and
  `save` still discards it, returning `Outcome<Unit>`. This task did not need it — the ViewModel
  never has to adopt a note it just created, because the row it opened already has an id. The task
  that needs it changes the return type there.
- **Carried forward, unchanged from T-002:** the row's `Untitled note` fallback is covered by no
  test and no image. It is a `stringResource` inside a private composable, so the only two routes to
  it are a rendered reference (blocked on the locale/CLDR lock in `knowledge/ISSUES.md`) or a
  host-side UI test (not available). Stated in `HomeScreenshotTest.kt` now, rather than deferred to
  a task again.
- **Not done, on purpose:** no populated-row reference image. `@Preview(locale = "en")` would pin
  the *language* of the row's date but not its *format* — `ofLocalizedDate` follows the JDK's CLDR
  data and this project pins no toolchain — so recording one today buys a case that fails on the
  next toolchain bump for a reason unrelated to the app, which teaches the next person to re-record.
  It waits for the threshold or the pin that `knowledge/ISSUES.md` already asks for.
- **Housekeeping:** the review subagent left `build-t004-review.log` at the repository root. It is
  git-ignored (it does not appear in `git status`), so it is invisible to the branch, and `rm` is
