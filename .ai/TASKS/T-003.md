# T-003 — User can create a note for today from Home

- **Status:** ✅ complete
- **Depends on:** T-002
- **Attempts:** 1 / 3

## Description

Wire the create path end to end, so a note can be written in the app rather than seeded in a test.

- New screen `ui/fragment/note/` — `NoteFragment`, `NoteUiState`, `NoteViewModel`, private
  `NoteLayout` with defaulted lambdas and a `@Preview`. Follow the screen spine in
  `.claude/figma-design-system.md`: the fragment owns the ViewModel and navigation, the layout is
  pure UI.
- Nav graph: add a `noteFragment` destination and a `toNote` action with arguments — the note id
  (`-1L` for a new note) and the target date (epoch-day). Navigate with `safeNavigate`, never
  `findNavController().navigate(...)` directly.
- The centre action button in `ui/component/CoreBottomBar.kt` currently toggles an unused
  `showBottomSheet` flag. Repoint it at the create action for today's date. It sits in a shared
  component, so give it a callback rather than hardcoding a destination inside it.
- The editor has **two** fields: a single-line title and a multi-line body (amendment A-001). The
  title may be left blank — do not block saving on it.
- `NoteRepository.save(note): Outcome<Unit>` (or equivalent non-throwing return per
  `.claude/repository-layer.md`) sets `createdAt` and `updatedAt` on insert.
- The editor must scroll rather than clip when the text exceeds the visible area, and the save
  action must stay reachable — put it in `CoreLayout`'s `topBar` or `bottomBar`, not inside the
  scrolling content.
- Saving returns to Home, where the new note is the first row.

### Scope taken on beyond the above — both Tier 1, both logged

- **The future-date rule (`knowledge/DOMAIN.md` rule 1) is implemented here, not in T-008**
  (amendment **A-006**). The rule's own text puts the enforcement point in the repository "so that
  no caller can bypass it"; this task is where the first write path exists, so a `save` that
  accepted any date would be code known to contradict a human-owned rule. **DoD criterion 10 is
  satisfied by this checkpoint.**
- **An existing note can be loaded and re-saved** (amendment **A-007**). The nav contract carries a
  note id, and honouring it was cheaper than shipping an id the screen would half-ignore — which
  would have blanked a real note. It also means both halves of `DOMAIN.md` rule 2 are tested in the
  checkpoint that introduces the stamping logic, rather than the `createdAt`-clobbering half being
  tested a task later.

## Fresh-Context Review

Reviewer given the staged diff, the task, `DoD.md`, `POLICIES.md`, `DOMAIN.md`, the house rule
files and `knowledge/`, and **not** given any implementation reasoning. 8 findings.

**2 Critical, both fixed in this iteration:**

1. **The editor was unusable with the keyboard open.** The app is edge-to-edge and `CoreLayout`
   zeroes its `contentWindowInsets`, so the window is not resized for the IME and nothing anywhere
   in `app/src/main` handled IME insets. The scroll viewport stayed full-screen height while the
   keyboard covered its bottom ~40%, and the scroll range (`content − viewport`) could never lift
   the covered strip into view — the user types into a line they cannot see. This is DoD criterion
   12's editor clause, and `NoteEditor`'s own KDoc claimed to prevent exactly this failure. Fixed
   with `Modifier.imePadding()` before `verticalScroll`, plus
   `android:windowSoftInputMode="adjustResize"` on `MainActivity`. **Below API 30 the fix is
   unverified** → `knowledge/ISSUES.md`.
2. **A double tap on Save wrote the note twice.** The re-entry guard cleared the moment the
   database returned — about five milliseconds — while the screen's exit animation keeps the
   composition alive and touchable for a few hundred more. A second tap in that window reached the
   store with the note still carrying `UNSAVED_ID`, and Room's `autoGenerate` handed out a second
   row: one intent, two identical notes on Home, no way to tell them apart. From Settings there was
   a second symptom — `savedTrigger` reaching 2 fires the navigation effect twice and pops Settings
   as well. Fixed by never lowering the guard on success (the screen is leaving) and lowering it
   only on failure. Covered by two new tests, one of which was mutation-checked above.

**2 Major, both fixed:**

3. **Three places asserted "no screen reads the clock", and five call sites contradicted it.**
   `Note.draft`'s KDoc, a new README bullet, and `NoteViewModelTest`'s KDoc. The true statement is
   narrower: the store owns the **timestamps**; the **date** is the caller's choice and is read from
   `LocalDate.now()` in four UI places. Worse than imprecision — the README bullet was formatted as
   a business rule beside the two real ones, and `knowledge/DOMAIN.md` contains no such rule. A rule
   invented in a README is a rule the next iteration implements as truth, and `DOMAIN.md` is
   human-owned precisely so that cannot happen. All three reworded; README now says out loud which
   two rules are the domain rulebook and that this third point is a convention serving them.
4. **Criterion 5 is not satisfied on the Settings path.** The criterion says saving "returns to
   Home"; from Settings, `safeNavigateUp()` returns to Settings and the new note is never shown.
   The task file required this decision to be made here and the code made it silently. Resolved by
   recording it as an assumption in `.ai/STATE.md` (reversible, one line to overrule) rather than
   forcing every save back to Home — which would be wrong for T-008, where a note added to a
   selected day belongs back on the Calendar screen.

**4 Minor.** Two filed to `knowledge/ISSUES.md` (unsaved text discarded on back / process death;
a refused save being a dead end — the latter becomes reachable by ordinary use at T-008). Two
accepted with reasons, recorded here rather than filed:

- **`NoteEditor` reads `LocalConfiguration.current.locales[0]` where `CoreFragment` provides
  `LocalLocale` for this purpose.** Both are correct in-app. `LocalConfiguration` was kept for
  consistency with `HomeNoteList` (T-002), and because `LocalLocale`'s default is
  `Locale.getDefault()` — the device locale, which is the exact answer the comment there warns
  against — so it is only correct *because* a Fragment overrides it, and a preview gets the wrong
  one. Worth unifying in T-009 with the strings audit; not worth two different idioms landing in
  two different tasks.
- **`save()` uses `viewModelScope.launch` where `.claude/viewmodel-layer.md` asks for
  `Dispatchers.IO` on writes.** A conflict between house rules, flagged here as those files
  instruct: `.claude/repository-layer.md` has `NoteRepositoryImpl.save` doing
  `withContext(ioDispatcher)` already, so adding `Dispatchers.IO` here would switch threads twice
  for one write. Staying on Main is also what makes the `saving` re-entry guard a plain `var`
  instead of something that needs synchronisation. Kept on Main deliberately.

Also verified by the reviewer and worth recording as *not* defects, since each was a plausible
failure: the future-date boundary matches `DOMAIN.md` word for word (`isAfter`, today inclusive,
refused as a value, enforced on every write path including edit); the ordering rule keeps its `id`
tiebreaker through the new write path; the nav argument types, defaults and sentinels line up
across all three files; and the `-1` → `0` id translation is correct against
`@PrimaryKey(autoGenerate = true)`.

## Notes

- `CoreBottomBar`'s `onCreateNote` has **no default**, deliberately. A defaulted `= {}` would let a
  future screen host the app's primary create action as a dead button — the state the bar was
  actually in before this task. The missing default earned its keep immediately: it broke
  `compileDebugScreenshotTestKotlin`, which `assembleDebug` and `testDebugUnitTest` both report
  green. That is now a `knowledge/PROJECT.md` entry.
- The centre button got its `contentDescription` (`add_note`) and the debounce the tabs beside it
  already had. Without the debounce two fast taps push two copies of the editor onto the back stack.
- **Carried to T-004:** Home rows become clickable and navigate through the `toNote` route, which
  already exists and already accepts a real note id. `NoteRepository.getNote` and the `noteId`
  argument have no in-app caller until then — exercised only by tests today, stated plainly rather
  than left to be discovered.
- **Carried to T-004:** `NoteDao.upsert` returns the generated row id and its KDoc advertises it;
  `save` discards it and returns `Outcome<Unit>`. Harmless now, but it is why the ViewModel cannot
  adopt the note it just created, which is what made the double-save defect possible in the first
  place. If T-004 needs the id, change the return type there.
- **Carried to T-004:** the row's `Untitled note` fallback (a note with neither title nor body) is
  still covered by nothing — inherited from T-002 and unchanged here.
