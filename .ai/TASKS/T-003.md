# T-003 — User can create a note for today from Home

- **Status:** pending
- **Depends on:** T-002
- **Attempts:** 0 / 3

## Description

Wire the create path end to end, so a note can be written in the app rather than seeded in a test.

- New screen `ui/fragment/note/` — `NoteFragment`, `NoteUiState`, `NoteViewModel`, private
  `NoteLayout` with defaulted lambdas and a `@Preview`. Follow the screen spine in
  `.claude/figma-design-system.md`: the fragment owns the ViewModel and navigation, the layout is
  pure UI.
- Nav graph: add a `noteFragment` destination and a `toNote` action with arguments — the note id
  (`-1L` for a new note) and the target date (epoch-day). Navigate with `safeNavigate`, never
  `findNavController().navigate(...)` directly.
- The centre action button in `ui/component/CoreBottomBar.kt` currently toggles an unused
  `showBottomSheet` flag. Repoint it at the create action for today's date. It sits in a shared
  component, so give it a callback rather than hardcoding a destination inside it.
- The editor has **two** fields: a single-line title and a multi-line body (amendment A-001). The
  title may be left blank — do not block saving on it.
- `NoteRepository.save(note): Outcome<Unit>` (or equivalent non-throwing return per
  `.claude/repository-layer.md`) sets `createdAt` and `updatedAt` on insert.
- The editor must scroll rather than clip when the text exceeds the visible area, and the save
  action must stay reachable — put it in `CoreLayout`'s `topBar` or `bottomBar`, not inside the
  scrolling content.
- Saving returns to Home, where the new note is the first row.

## Acceptance

Maps to DoD criteria 5 and the editor half of 12.

- Build, unit tests and lint succeed.
- A unit test proves `save` on a new note sets `createdAt` and `updatedAt`, and that the saved note's
  date is today when created from Home.
- The nav-graph destination and action exist and the argument types match what the fragment reads.
- Recorded as **needing human inspection** (class (I) until host-side UI tests exist): tapping the
  centre button opens an empty note, typing and saving returns to Home with the note at the top.

## Notes

- `CoreBottomBar` is used by every top-level screen. Changing its centre button affects Home and
  Setting alike — decide there what "create" means when the current screen is not Home, rather than
  discovering it later.
- The date argument exists from the start even though only "today" is passed here. T-008 passes a
  selected past date through the same route; adding the argument now avoids reshaping the navigation
  contract later.
- **Give that centre button a `contentDescription`.** It is `null` today
  (`CoreBottomBar.kt`, the `Icons.Rounded.Add` icon), which is survivable while the button does
  nothing but makes the app's primary create action unreachable to a screen reader the moment this
  task wires it up. Noticed in T-001 while repointing the button's colours at the theme; left alone
  there because T-001 was a theme task and this belongs to whoever gives the button its behaviour.
  Add a string named for its own words (e.g. `add_note`), and remember A-003 — it needs a
  `values-de/` entry in the same checkpoint or lint fails.
- **The selected bottom-bar tab has no colour distinction.** `BottomBarElement` paints both the
  selected and unselected icon in `onBackground`; the only signal that a tab is active is that its
  text label appears at all. Pre-existing (both were `Color.White` before T-001), but T-001 gave the
  app a real `primary`, so tinting the active item with it is now a one-line change — and this task
  is already inside that file.
