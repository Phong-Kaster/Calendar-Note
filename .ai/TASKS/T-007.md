# T-007 — Selecting today or a past day shows that day's notes, with an empty state

- **Status:** ✅ complete — iteration 9, 2026-09-11
- **Depends on:** T-006 ✅
- **Attempts:** 1 / 3

## Description

Make the calendar selection mean something.

- Selecting today or any past day loads that day's notes through
  `NoteRepository.notesForDateFlow(date)` (backed by the `observeByDate` DAO query added in T-002)
  and shows them in a scrolling list beneath the grid, on the same screen (decision A4 in the DoD).
- Explicit empty state when the selected day has no notes. A blank region reads as a load failure,
  not as "nothing here yet".
- Tapping a note in that list opens it in the Note screen, the same route Home uses.
- The whole screen scrolls: grid plus a variable-length list will not fit on a short device, and a
  fixed-height layout pushes the list — and later the add action — off the bottom.
- Mark days that have notes in the grid. The marker must contrast with the cell fill in **every**
  combination: has-notes on a normal cell, on today's cell, and on the selected cell.

### Fresh-context review

Re-run with a clean context against the full diff. **0 Critical, 1 Major, 6 Minor.** All seven
addressed; none filed.

1. **Major — the day list showed the previous day's notes under the new day's heading.** A tap moves
   `selectedDate` synchronously while the store's answer for the new day arrives a query later, so
   there was a window where the heading named day D and the rows below were day D-1's. Invisible to
   the suite, because the fake answers inline and the unconfined dispatcher closes the window.
   **Fixed by making the bad state unrepresentable rather than unlikely**: the ViewModel stores the
   notes *with* the day they answer for (`loadedDay` / `loadedDayNotes`) and `notesForSelectedDay` is
   a derived `val` that hands them over only while the two agree. The honest cost is written into its
   KDoc — a day that has notes may draw its empty message for a frame before the query returns.
2. Minor — nothing held the *ViewModel's* per-day list to `updatedAt` descending: `noteOn()` gave
   every fixture the same timestamp and the one multi-note assertion called `.sorted()`. Fixed:
   `noteOn` takes `updatedAt`, and a new test asserts the exact order (M2/M6 aside, this is what M2
   would have hit at the ViewModel layer).
3. Minor — `asking for one day returns that day's notes and nobody else's` did **not** catch the
   mutation its own comment claimed (forwarding `observeAll` and filtering in Kotlin returns the same
   list). Fixed: `FakeNoteDao` records `daysAskedFor`, and a new test asserts the per-day query was
   the one used. M3 confirms it, and confirms nothing else catches it.
4. Minor — `FakeNoteDao.observeByDate` was a dead snapshot, so a `.take(1)` in the repository would
   have frozen the day list in production with every test green. Fixed: the fake is live, and a new
   test collects across a write. M4 confirms it.
5. Minor — two tests claimed guards they did not provide. The paging test now counts subscriptions
   (`FakeNoteRepository.dayReaders`), which is what actually defends the `distinctUntilChanged` key
   (M6); the redundant repository test is kept with an honest comment.
6. Minor — the day heading was `maxLines = 1` + ellipsis, and the reviewer argued the German
   full-style date would truncate at 288–328dp. **The fix was taken and the reasoning was wrong** —
   see below.
7. Minor — `collectNotes`'s KDoc implied an efficiency the code does not have (`notesFlow` is
   `SELECT *`; only the *retention* of every note is avoided, not the reading of them). KDoc
   corrected; the `SELECT DISTINCT date` query it suggests is named as a thing to do when a table
   large enough to notice exists, not now.

**Finding 6 is the interesting one, and the picture settled it against the reviewer.** Recording
`DayNotesGermanHeading` at 288dp of content — a 320dp screen, the narrow end of what this app
supports — shows "Donnerstag, 24. September 2026" fitting comfortably on one line. The arithmetic in
the finding was simply wrong. `maxLines = 2` stayed as insurance for a longer locale or a large
accessibility font scale, and both the component comment and the test KDoc now say plainly that no
shipped locale overflows and that the image is **not** evidence a wrap was needed.

Recording that case also re-ran the undersized-preview trap: the first attempt at 120dp tall came
back as a heading above empty black, silently dropping the empty-state message. Caught by looking at
the image, which is the only way it could have been.

## Notes

- The has-notes marker on the selected cell is the exact overlap `POLICIES.md` warns about — a dot
  painted in the same role as the container it sits on is invisible, and every automated check stays
  green. Check the combination, not the two states separately. The prior run on
  `loop/todo-calendar-screens` shipped exactly this bug; its screenshot case is called
  *"Day cell - today with notes"*. **Already handled in T-006; verified unregressed here.**
- **"A selected date with no notes used to render an unexplained blank gap"** — the prior run's own
  words, and its `NoteListEmptyDay` case exists to pin the fix. Written here as `DayNotesEmptyDay`,
  and M8 proves it is the only thing that catches a regression.
- **Why the day section is a plain `Column` and not a `LazyColumn`.** The task asks for the whole
  screen to scroll as one page, and `CalendarFragment`'s content is already a `verticalScroll`
  `Column`; a lazy list nested in a scrolling parent throws at measure time for being handed an
  infinite height. The trade — every row composed rather than only the visible ones — is affordable
  because this is one day's notes, not Home's every-note list. Written into the component's KDoc.
- **Why the day label is passed in as a `String`.** `CalendarDayNotes` does no date formatting, so
  its reference images carry no formatter output and are not host-locale-locked. This is the shape
  `knowledge/ISSUES.md` § *The Note editor has no reference image* suggests for `NoteEditor`, and it
  works — **that entry's suggested fix is now demonstrated, if a later task wants to take it.**
- **`NoteRow` was extracted from `HomeNoteList` into `ui/component/NoteSummaryRow.kt`** rather than
  copied. Home renders identically — the `showDate` parameter defaults to `true` and every existing
  reference image is byte-unchanged, which is the evidence for that claim.
