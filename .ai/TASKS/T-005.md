# T-005 — User can delete a note behind a confirmation step

- **Status:** pending
- **Depends on:** T-004
- **Attempts:** 0 / 3

## Description

Deletion is the only irreversible action in the app, so it gets a confirmation step —
`POLICIES.md` § User-Interface Defects treats one-tap irreversible deletion as a defect, not a
shortcut.

- Add a delete action to the Note screen (existing notes only — it makes no sense on an unsaved new
  note; hide it rather than disabling it silently).
- Deleting always passes through a confirmation. Use the existing `ui/component/CoreBottomSheet.kt`
  or a Material dialog — check what the repository already has before writing a new one.
- The confirming control must be **visually distinct** from the cancelling one. Distinct means a
  different colour role and a different emphasis, not just different label text.
- `NoteRepository.delete(note)` removes the row; Home's flow drops it without a manual refresh.
- Follow the mutually-exclusive-overlay pattern from `.claude/jetpack-compose-ui.md` if the Note
  screen ends up with more than one overlay: the `when` block lives in `ComposeView()`, never inside
  `NoteLayout`.

## Acceptance

Maps to DoD criterion 7.

- Build, unit tests and lint succeed.
- A unit test proves `delete` removes the note from the emitted list.
- The diff shows the confirmation is unconditional: no code path reaches `delete` from a single tap.
- Recorded as **needing human inspection** (class (I)): whether the confirming control is visually
  distinct from the cancelling one. This is perceptual — no command can prove it.
