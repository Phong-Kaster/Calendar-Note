# T-005 — User can delete a note behind a confirmation step

- **Status:** pending
- **Depends on:** T-004, T-010
- **Attempts:** 0 / 3

## Description

Deletion is the only irreversible action in the app, so it gets a confirmation step —
`POLICIES.md` § User-Interface Defects treats one-tap irreversible deletion as a defect, not a
shortcut.

- Add a delete action to the Note screen (existing notes only — it makes no sense on an unsaved new
  note; hide it rather than disabling it silently).
- Deleting always passes through a confirmation. Use the existing `ui/component/CoreBottomSheet.kt`
  or a Material dialog — check what the repository already has before writing a new one.
- The confirming control must be **visually distinct** from the cancelling one. Distinct means a
  different colour role and a different emphasis, not just different label text.
- `NoteRepository.delete(note)` removes the row; Home's flow drops it without a manual refresh.
- Follow the mutually-exclusive-overlay pattern from `.claude/jetpack-compose-ui.md` if the Note
  screen ends up with more than one overlay: the `when` block lives in `ComposeView()`, never inside
  `NoteLayout`.
- **Resolve `knowledge/ISSUES.md` § *A note that fails to load opens as a blank editor, and saving
  it writes a second note* here — it is a prerequisite of this task, not a follow-up.** Delete is
  what turns "the note you opened is not there" from a disk-fault curiosity into ordinary use: a
  note deleted on one surface and opened from a stale Home row currently comes up as a blank editor
  whose save **inserts**, resurrecting the deleted note as a duplicate. Added by the fresh-context
  review of T-004 (finding 2); the entry says what would resolve it and what not to do.

## Acceptance

Maps to DoD criterion 7.

- Build, unit tests and lint succeed.
- A unit test proves `delete` removes the note from the emitted list.
- A unit test proves that opening a note the store cannot produce does **not** end in a second row
  being written (the ISSUES entry above). Note that the existing `NoteViewModelTest` case *a note
  that has since been deleted opens as a fresh one for the day asked for* pins the current
  behaviour, so resolving this means changing that test on purpose, not working around it.
- The diff shows the confirmation is unconditional: no code path reaches `delete` from a single tap.
- **Screenshot evidence** (harness from T-010): a reference image of the confirmation, approved once
  by the human for the "confirming control is visually distinct from the cancelling one" clause, and
  defended by `:app:validateDebugScreenshotTest` thereafter.
