# T-005 — User can delete a note behind a confirmation step

- **Status:** ✅ complete
- **Depends on:** T-004, T-010
- **Attempts:** 1 / 3

## Description

Deletion is the only irreversible action in the app, so it gets a confirmation step —
`POLICIES.md` § User-Interface Defects treats one-tap irreversible deletion as a defect, not a
shortcut.

- Add a delete action to the Note screen (existing notes only — it makes no sense on an unsaved new
  note; hide it rather than disabling it silently).
- Deleting always passes through a confirmation. Use the existing `ui/component/CoreBottomSheet.kt`
  or a Material dialog — check what the repository already has before writing a new one.
- The confirming control must be **visually distinct** from the cancelling one. Distinct means a
  different colour role and a different emphasis, not just different label text.
- `NoteRepository.delete(note)` removes the row; Home's flow drops it without a manual refresh.
- Follow the mutually-exclusive-overlay pattern from `.claude/jetpack-compose-ui.md` if the Note
  screen ends up with more than one overlay: the `when` block lives in `ComposeView()`, never inside
  `NoteLayout`.
- **Resolve `knowledge/ISSUES.md` § *A note that fails to load opens as a blank editor, and saving
  it writes a second note* here — it is a prerequisite of this task, not a follow-up.** Delete is
  what turns "the note you opened is not there" from a disk-fault curiosity into ordinary use: a
  note deleted on one surface and opened from a stale Home row currently comes up as a blank editor
  whose save **inserts**, resurrecting the deleted note as a duplicate. Added by the fresh-context
  review of T-004 (finding 2); the entry says what would resolve it and what not to do.

## What was built

- **`NoteRepository.getNote` now returns `Outcome<Note?>` instead of `Note?`** — the prerequisite
  above. Three answers where there used to be two: the note, `Success(null)` for "I looked and it
  is not there", and `Error` for "I could not look". The old single `null` collapsed the last two,
  and the screen had to guess.
- **`NoteRepository.delete(note): Outcome<Unit>`**, refusing a note that carries `Note.UNSAVED_ID`
  rather than letting Room's `@Delete` match no row and report success.
- **`NoteViewModel`** gained `askToDelete()` / `dismissDelete()` / `delete()`, a `deleting`
  in-flight guard mirroring `saving`, and — in `openNote` — two deliberate exits in place of the
  old fall-through to a blank draft: `NoteProblem.Gone` and `NoteProblem.Unreadable`.
- **`ui/fragment/note/model/NoteProblem.kt`** — a screen-local enum, per the house rules'
  `model/` convention. Three reasons the screen cannot go on, each with its own message.
- **`component/NoteDeleteConfirmSheet.kt`** — `CoreBottomSheet` wrapping a
  `NoteDeleteConfirmContent` that is public and separately renderable, which is what lets the
  screenshot case pin it.
- Eight strings in both locales, a `@PreviewTest` case and its reference image, and the README
  feature table and package tree.

## Fresh-Context Review

Reviewer given the diff, the task, `DoD.md`, `POLICIES.md`, `DOMAIN.md`, `knowledge/`, the house
rule files and the evidence — and **not** given any implementation reasoning. It re-ran all four
Gradle tasks itself rather than taking the evidence on trust. **10 findings: 1 Critical, 3 Major,
6 Minor. All resolved — 8 fixed here, 2 filed.**

**1 Critical — fixed.** **`save()` stayed armed after a successful delete, and one tap put the
deleted note back.** The success branch cleared `confirmingDelete` and raised `deletedTrigger` but
left `openedNote` non-null and `saving` false. The screen leaves on that trigger — and leaving is
animated: `toNote`'s `popExitAnim` runs for `config_longAnimTime` (**500 ms**), and a legacy View
animation leaves the exiting view in the hierarchy, un-transformed for hit-testing, taking touches
the whole time. The Save control is still composed and still clickable in that window, and it
would have found a perfectly valid note — real `id`, real `createdAt`. `upsert` is
`onConflict = REPLACE`, so the row came **back**, one frame after the user was told it was deleted,
at the top of Home because `updatedAt` was fresh. `knowledge/ISSUES.md` names that exact outcome
as an unacceptable answer. Fixed by dropping `openedNote` (and `deletable`) in the success branch,
so `save()` returns at its own first line; covered by
`a save after the note has been deleted does not put it back` and mutation-checked.

**The reviewer's sharpest observation was about the shape of the bug, not the bug:** a second tap
on *Delete* was correctly refused by the `deleting` guard, so only Save was unguarded — the
asymmetry "looks accidental rather than reasoned". It was. The `saving` guard's own KDoc had
already written down the exact argument that condemns it, four functions higher up. **That is the
confident-comment pattern for the third iteration running**, and this time the comment was not
merely near the defect, it *described* it.

**3 Major — all fixed.**

2. **The resolved `ISSUES.md` entry was still in the file**, and after this diff every sentence in
   it was false — it described `getNote` returning `null` and cited a test that had been reversed
   and renamed. `POLICIES.md` § Reconciliation Rules requires deletion in the same checkpoint, and
   the next iteration reads that file at Orient. (Removed, along with the stale test count in
   `PROJECT.md`. As it happens both were already done by the time the review landed, but the
   finding stands and is recorded because the reviewer could only see the tree, not the intent.)
3. **The delete guard was narrower than the KDoc justifying it.** The comment argued that Room
   "would match no row and report nothing wrong" — true of **every** absent id, while the code
   guarded only `Note.UNSAVED_ID`. Any other missing row (deleted on a second surface, a stale id,
   the Calendar screens T-006/T-008 will add) returned `Success`, raised `deletedTrigger` and
   showed "Note deleted" for a delete that removed nothing. Fixed by making `NoteDao.delete`
   return `Int` and treating `0` as an error — which closes the general case the comment already
   claimed to close, rather than narrowing the comment to match the code.
4. **`askToDelete()` had no guard at all**, while `delete()` had three. On a brand-new note it
   would open a confirmation for a draft, and confirming produced "the note could not be deleted"
   — the wrong sentence for "there was never anything there". Only the hidden top-bar control kept
   it off screen, which is the same "the only caller today" reasoning `delete()`'s own comment
   declines to rely on. Now gated on `deletable`.

**6 Minor — 4 fixed, 2 filed.**

5. **Fixed — three new tests could not fail for the reason they stated.** `a brand-new note offers
   no delete action` asserted a field's declared default on a path that never writes it; `the
   problem clears once it has been shown` never checked the problem was set first; and
   `nothing is written or removed before a note has been opened` returned at the confirmation
   guard, never reaching the "is there a note?" guard its comment was about. All three now
   exercise what they claim — and the seventh mutation above proves the third one does.
6. **Fixed — the reference image was recorded on the wrong ground colour** (see the note above the
   mutation table). Fixing it properly turned up a second trap: writing the new parameter as
   `ground: Color = MaterialTheme.colorScheme.background` would evaluate the default in the
   *caller's* composition, outside `ScreenshotScaffold`'s own `MyApplicationTheme`, against
   Material's **light** baseline — silently re-recording every reference in the project on a white
   ground. The parameter is a `ScreenshotGround` enum resolved inside the theme for exactly that
   reason. → `knowledge/PROJECT.md`.
7. **Fixed — the new destructive control had a ~31dp touch target, 4dp from Save**, and lacked the
   `onClickLabel` / `interactionSource` / `ripple` triple the house rules require — in a diff whose
   *own* sibling component documents the 48dp reasoning. Now 48dp via `defaultMinSize` after the
   click (nothing is painted there, so the box costs no pixels), 8dp of dead space to Save, and
   the full click semantics.
8. **Filed — a sheet dismissed by its own button vanishes instead of animating out.**
   `CoreBottomSheet` only calls `sheetState.hide()` on the swipe/scrim path. It is a shared
   primitive with two other callers, so changing how it closes belongs to its own change, not to
   this one. → `knowledge/ISSUES.md`.
9. **Filed — the `Gone`/`Unreadable` exit is a one-way door.** `problem` is consumed *before*
   `safeNavigateUp()`, which swallows exceptions — so a pop that does not happen leaves the user
   on a blank editor with no second trigger. Low probability, zero recovery, and the real fix needs
   the Fragment to observe the pop, which nothing here does yet. → `knowledge/ISSUES.md`.
10. **Fixed — an unrecorded divergence from `.claude/repository-layer.md`.** That rule file maps
    "single item fetch, null = not found" to a bare `T?`; `getNote` now returns `Outcome<Note?>`.
    The change is right and is what `ISSUES.md` asked for, but the house rules require a conflict
    with a rule file to be called out, and nothing recorded that this is now the local convention —
    so the next iteration could flatten it back. → `knowledge/PROJECT.md`.

## Notes

- **What the new screenshot case does *not* prove, stated in the file itself:** it renders
  `NoteDeleteConfirmContent` directly, not `NoteDeleteConfirmSheet`. If the sheet stopped passing the
  content through, or `NoteFragment` stopped showing the sheet, the case would still pass. A
  `ModalBottomSheet` renders into its own window and what layoutlib does with that host-side is not
  established here, so the honest trade was to pin the part that certainly renders and say plainly
  which part is not pinned. The same gap exists one floor up in `HomeScreenshotTest`.
- **It also does not prove criterion 2.** A screenshot cannot tell `Color.White` from
  `colorScheme.onBackground`. Criterion 2 is carried for this diff by a source check
  (`grep -E 'Color\.Black|Color\.White|Color\(0x'` over `ui/fragment/note/` → no matches; the one
  `Color.Transparent` default in `NoteDeleteConfirmAction` is an absence of fill, not a colour
  choice) and by the fresh-context review.
- **`NoteDeleteConfirmContent` is public where the house rules would default to private**, because
  `app/src/screenshotTest/` is a separate source set and cannot see a private composable. This is
  the same trade `HomeNoteList` made in T-002. The layout it lives inside, `NoteLayout`, stays
  private as the rules require.
- **Carried forward, unchanged:** `NoteDao.upsert` still returns a row id that `save` discards. This
  task did not need it either — `delete` takes the whole note and only reads its `id`.
